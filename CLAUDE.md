# Pixel Dungeon (MUB) - match3-rpg-basic

Vanilla HTML/CSS/JS match-3 RPG (solo/PvP/co-op) backed by Supabase (anon auth, Realtime, Postgres+RLS). No build step, no bundler - every file is a plain `<script>` tag in `index.html`, loaded in this order: `graphics.js`, `i18n.js`, `i18n-dict.js`, `sound.js`, `economy.js`, `items.js`, `achievements.js`, `sharedboard.js` (the board engine all three modes use - must load before `game.js`, whose boot runs in a microtask right after it), `game.js`, `pvp.js`, `coop.js`.

## Hard rules, learned the expensive way

**Always look up JS-targeted DOM elements by `id`, never by class or tag.** `pvp-modal` and `coop-modal` sit earlier in `index.html` than the main game area, and several UI pieces (`.grid`, `.stat-box`) reuse the same class across all three modes for shared CSS sizing. `document.querySelector('.grid')` or `document.querySelector('.stat-box div:first-child')` silently returns the wrong mode's element instead of erroring - this caused two real, only-visually-detectable bugs (the class-selection screen rendering inside a hidden PvP modal; the picked class name never appearing on the visible HUD). `document.getElementById(...)` doesn't have this failure mode. If you need to verify a UI change actually renders where a user would see it, don't trust computed-style/DOM-state checks alone - take a screenshot too (getComputedStyle has also been observed to under-report values like `opacity` in this browser tooling even when the real render is correct).

**Never merge or push to `main` without the user personally testing in a browser first.** They must give explicit approval (an unambiguous "merge it" or a direct confirmation right after being offered exactly that choice) - passing your own testing is not enough. When asked to build a batch of features autonomously (the user often steps away for hours and explicitly asks not to be interrupted with questions), create a new feature branch off `main`, implement and test thoroughly with the local dev server, commit, push, and repoint GitHub Pages at that branch (`gh api repos/.../pages -X PUT` then a `pages/builds` POST to force a rebuild) so a live link is ready - but still wait for their test and go-ahead before merging.

**`supabase/schema.sql` is a full replace, not a migration.** Tables are declared `drop table if exists ... cascade; create table ...` rather than incremental `alter table`s. The user must manually re-run the entire file in the Supabase SQL Editor for any schema change to take effect (no automated deploy path exists for this) - always call out explicitly what will break and what data gets wiped until they do. Functions/policies/triggers use `create or replace` / `drop ... if exists` so re-running is idempotent for those; new tables using `drop table ... cascade` are NOT idempotent-safe for existing data.

**Currency and item grants must go through a security-definer RPC, never a direct client `.update()`/`.insert()`.** `wallets` has no client-writable UPDATE policy and `player_items` has an insert trigger (`validate_player_item_insert`) that checks new rows against reference tables (`item_bases`, `item_rarity_bounds`, `item_fixed_defs`) mirroring `items.js`'s own catalog - RLS alone only ever checks row ownership, never whether a value makes sense. `earn_currency()`, `purchase_item()`, and `resolve_betrayal()` are the three trusted paths gold/items can move through; if you add a new way to earn currency or items, add a new bounded RPC rather than exposing a raw table write. The reference tables must stay in sync with `items.js`'s actual catalog by hand (there's no single source of truth across languages here - the trade-off was accepted to avoid porting the full random-roll algorithm into SQL) - when adding a new item base or unique legendary in `items.js`, add the matching row in `schema.sql` too, in the same commit.

## Testing

There is no Node.js in this dev environment and the game's source files are plain global-scope browser scripts, so `tests/index.html` is an in-browser harness (zero dependencies). Details and how-tos: `tests/README.md`. The essentials:

- **Worlds, not fixtures.** Each test runs the REAL `index.html` in an iframe ("world"), rewritten on the fly to load `tests/supabase-stub.js` (in-memory tables, RPC table matching `schema.sql`'s return shapes, shared fake realtime bus) instead of the Supabase CDN. There is no hand-maintained copy of the DOM anymore - the old `tests/fixture.html` drifted ~30 versions behind and was deleted. Read/drive game globals (even `let`/`const`) with `world.g('expr')`.
- **Deterministic.** `tests/world-prelude.js` seeds `Math.random`, fakes `setTimeout`/`setInterval`/`Date.now` (advance with `world.tick(ms)` / `world.settle()`), seals `localStorage`, and fails a test on any uncaught error. PvP/co-op tests run two real worlds over one bus (`settleAll`).
- **What's covered:** board rules + the shared board engine (`sharedboard.js`), combat math, a seeded golden-master solo run, items, schema.sql <-> items.js / i18n / DOM-rule contracts, PvP + co-op end to end, the shared Pixi renderer and effects, layout at 13 viewport sizes (the mobile rule), auto quality.
- **CI** (`.github/workflows/ci.yml`): job `test` runs the page headlessly (`tests/run-ci.mjs`); job `sql` applies `supabase/schema.sql` **twice** to a real Postgres (after `tests/sql/00_supabase_shim.sql`) and runs `tests/sql/10_rls_and_rpcs.sql` (earn_currency bounds, no direct wallet writes, item insert validation, purchase_item). Pages only rebuilds from `main` when both pass.

Still true: there is no staging database - the `sql` job proves the file applies and its RPC/RLS logic holds on plain Postgres, but the user must still re-run `schema.sql` in the Supabase SQL Editor for any schema change to reach production; say so explicitly.
